# Multi-Product Operating Model

## Purpose

Reuse engineering standards across a product portfolio without erasing product-specific context, ownership, priorities, or risk.

## Shared core and product profiles

Maintain a versioned framework core and a separate profile for each product. The shared core defines common principles and minimum controls. Each product profile defines its users, outcomes, stack, architecture, risk context, regulatory scope, teams, tools, tailoring, and exceptions.

## Portfolio decisions

At portfolio level, coordinate strategic alignment, shared platform investments, cross-product dependencies, capacity constraints, common security controls, vendor relationships, and shared reliability capabilities. Do not centrally approve ordinary product decisions unless authority is explicitly delegated.

## Shared platforms and services

For shared components, define service ownership, interface contracts, consumers, versioning, support commitments, change communication, service objectives, cost allocation where relevant, and deprecation process. Product teams remain responsible for understanding their dependency impact.

## Governance and metrics

Keep product roadmaps, backlogs, risk registers, customer data, architecture decisions, and release approvals separate unless a shared register is intentionally established with clear ownership and access controls. Use common definitions for portfolio reporting while allowing product-specific outcome measures.

## Onboarding another product

1. Create a distinct product profile.
2. Run the discovery and maturity assessment for that product.
3. Identify which core practices apply and any justified exceptions.
4. Map the product's existing artifacts and toolchain.
5. Approve a tailored adoption plan.
6. Validate product-level and cross-product dependencies.

## Avoid

Do not impose one team's workflow on every product, merge separate product backlogs into a single undifferentiated list, or allow one product's constraints to become global defaults.
