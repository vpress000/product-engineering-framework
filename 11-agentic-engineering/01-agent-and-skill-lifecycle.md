# Agent and Skill Lifecycle Management

## Purpose

Define a controlled lifecycle for reusable agentic engineering assets: skills, agents/subagents, reusable prompts, tool configurations, and evaluation suites. This lifecycle governs both platform-native assets and assets optimized through Microsoft SkillOpt.

## Scope and terminology

- **Skill:** A reusable procedure or capability description invoked by an agent under defined conditions.
- **Agent/subagent:** A bounded execution role with a responsibility, context, tools, permissions, and handoff contract.
- **Prompt asset:** A reusable instruction/task specification that is not necessarily a skill.
- **Evaluation suite:** A versioned task set, expected outcomes, scoring rules, and split/exposure metadata.
- **Optimizer:** A tool that proposes changes to a skill. In PEOF v1.4, Microsoft's SkillOpt repository is the supported reference implementation for research-driven optimization and usage-driven Sleep workflows.
- **Agentic asset:** Any of the above that can affect agent behavior or the work product.

Keep platform-specific file formats in the relevant integration layer. This lifecycle is platform-independent.

## Lifecycle

| Stage | Required activity | Exit evidence |
|---|---|---|
| 1. Identify | State recurring problem, users, frequency, risk, and reuse value | Problem statement and value hypothesis |
| 2. Specify | Define scope, triggers, inputs, outputs, boundaries, tools, data access, owner, success criteria | Approved asset specification |
| 3. Design | Choose skill, agent, prompt, automation, or no artifact; apply least privilege | Reviewed design and threat/data assessment where relevant |
| 4. Build | Author a bounded, version-controlled candidate | Candidate artifact and diff |
| 5. Baseline | Freeze an initial version and representative tasks | Baseline version/hash and manifest |
| 6. Evaluate | Run deterministic checks and relevant SkillOpt or manual evaluation | Baseline evaluation report |
| 7. Optimize (when justified) | Use SkillOpt research training or Sleep usage learning; keep the workflows separate | Candidate artifact, run provenance, gate evidence |
| 8. Review and approve | Review diff, behavior, risk, permissions, data, cost, and evidence | Named approval and adoption decision |
| 9. Publish | Promote exact reviewed candidate to approved location | Release record, version, hash, receipt, rollback point |
| 10. Monitor | Review usage, failures, regressions, and cost within approved data boundary | Periodic health report |
| 11. Improve or retire | Re-evaluate, revise, deprecate, or retire | New approved version or retirement record |

## Lifecycle states

Use `proposed`, `draft`, `evaluating`, `approved`, `active`, `deprecated`, `retired`, and `rejected`. A file generated by an optimizer is still a candidate; it is not approved because an optimizer gate passed or because the file exists.

## Mandatory asset record

Record stable asset ID/name/type/platform, purpose/owner/scope/triggers, version/hash, canonical and published paths, inputs/outputs/dependencies, tool permissions, data classification, evaluation suite/version, model/provider and SkillOpt commit where applicable, latest results, limitations, approval, change history, and rollback target.

## SkillOpt integration rule

For automated optimization, follow [`../12-skillopt-integration/01-integration-architecture.md`](../12-skillopt-integration/01-integration-architecture.md). SkillOpt is an execution tool, not the governance authority. PEOF retains ownership of task split integrity, product context, privacy review, risk gates, approval, adoption, and rollback. Do not assume SkillOpt-Sleep's project scope is repository access; verify backend isolation and use a project benchmark adapter for end-to-end code tasks.

## Decision rules

1. Do not create an agent when a skill/checklist is sufficient.
2. Do not optimize a one-off skill without a repeat-use case and measurable goal.
3. Keep the asset, evaluator, task set, adapter, and model/backend versions separately traceable.
4. Preserve an approved baseline before optimization.
5. A held-out gate is necessary evidence, not blanket proof of general improvement.
6. Human approval is required before adopting a shared or product-critical asset.
7. Never auto-adopt by default.
8. Preserve evidence and deliberate retirement history.

## Tailoring

A solo developer may use Git, the templates, one SkillOpt checkout, and a small evaluation manifest. Larger teams may add CI, an asset catalogue, and automated review. Do not add a separate platform unless it is worth operating.
